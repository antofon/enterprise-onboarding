# Meridian target platform

Meridian is the fictional B2B SaaS platform the customer is migrating into. This directory is what an implementation engineer would be handed on day one: the entity model, the required fields, the enums, the relationships, the API, and the validation rules. The machine-readable versions live in [`../schema/`](../schema/) and are generated from the Pydantic models in `app/target/schema.py` (a unit test fails if they drift).

## Entity model

```
Organization 1 ---- * Contact
             1 ---- * Subscription
             1 ---- * Activity
```

An **Organization** is the customer account. **Contacts** are the people at it. A **Subscription** is what it pays for. **Activity** is optional history (invoices, payments, tickets, logins, notes). Every child record carries the parent's `organization_id`, and the parent must exist first.

Identifiers are supplied by the integrator, not generated by Meridian. Use the customer's stable legacy ids (an account number, a contact reference) so that re-running a migration is idempotent: the same id with the same content is a no-op, the same id with different content is a `409 conflict`.

## Validation rules

Field-level rules are in the tables above and enforced by the models: unknown enum values, unknown fields, malformed emails and phones, and out-of-range numbers are all rejected.

Cross-record rules:

1. An organization must exist before any contact, subscription or activity references it.
2. Ids are unique per entity. Same id + same content is idempotent; same id + different content is a conflict.
3. At most one contact per organization has `is_primary = true`.
4. An organization with contacts should have exactly one primary contact. Missing primary is a warning, not a rejection.
5. `email` is unique within an organization.
6. An `inactive` or `churned` organization cannot hold a `trial` or `active` subscription.

## API

All endpoints are under `/target/v1`, served by the same process as the onboarding tool in this repo (in real life it would be a separate service; the base URL is configuration).

| method | path | behavior |
|---|---|---|
| POST | `/organizations` | create; `409` on id conflict with different content; `422` on validation failure |
| GET | `/organizations/{organization_id}` | fetch |
| POST | `/contacts` | create; `422` if the organization does not exist |
| GET | `/contacts/{contact_id}` | fetch |
| POST | `/subscriptions` | create; `422` if the organization does not exist or rule 6 fails |
| GET | `/subscriptions/{subscription_id}` | fetch |
| POST | `/activities` | create |
| GET | `/stats` | row counts per entity, used by reconciliation |

Failure injection, for exercising the migration runner's error handling, is controlled by request headers documented with the API on Day 4 (random 500s, slow responses, malformed bodies).
